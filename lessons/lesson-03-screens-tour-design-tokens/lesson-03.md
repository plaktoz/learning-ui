# Lesson 3 — The 5-Screen Tour, shadcn vs. Custom, and Design Tokens

**Phase:** 1→2 · **Time:** 90 min · **Grounded in commits:** `1d561fc`, `5298c46`, and the current `frontend/src/app/` tree

## Recap

Lesson 2 covered what a component is and how to read props/state/Tailwind
off the component-library commit. This lesson zooms out to the whole app —
what screens exist, which pieces are off-the-shelf vs. hand-built, and why
color/spacing never appear as raw values.

## Objective

By the end of this lesson you can look at any of the 5 screens and know
what you're looking at, recognize a shadcn primitive vs. a custom
component, and explain why tokens exist instead of hardcoded colors.

## Main activity

### The 5 screens

Run `find frontend/src/app -name "page.tsx"` yourself. You'll find:

| Route | File | Screen |
|---|---|---|
| `/` | `app/page.tsx` | Notes dashboard (grid of note cards, filterable by folder/tag) |
| `/notes/[id]` | `app/notes/[id]/page.tsx` | Note editor (title, body, folder select, tag toggles) |
| `/folders` | `app/folders/page.tsx` | Folders & tags management |
| `/search` | `app/search/page.tsx` | Search |
| `/settings` | `app/settings/page.tsx` | Settings (theme) |

Every one of these `page.tsx` files is thin — a handful of lines. Open
`frontend/src/app/page.tsx`:

```tsx
export default async function Home() {
  const user = await getCurrentUser();
  if (!user) redirect("/login");
  return (
    <AppShell user={user}>
      <Suspense fallback={null}>
        <NotesDashboard />
      </Suspense>
    </AppShell>
  );
}
```

The **route file** (`page.tsx`) only does two things: decide whether you're
allowed to see this page (the auth check — Lesson 8 covers where
`getCurrentUser` actually looks), and wire the real screen component
(`NotesDashboard`) into the shared `AppShell` frame. All the actual screen
logic lives in `frontend/src/components/notes/notes-dashboard.tsx` — this
split (thin route file, fat component) is consistent across all 5 screens,
so once you've read one `page.tsx`, you know the shape of all of them.

`[id]` in the folder name `notes/[id]/` is Next.js's syntax for a **dynamic
route segment** — `/notes/abc123` and `/notes/xyz789` both match this one
file, and the matched value (`abc123`) is available inside as `noteId`.

### shadcn primitives vs. custom components

Open `frontend/src/components/ui/`. Everything in here (`button.tsx`,
`input.tsx`, `textarea.tsx`, `card.tsx`, `badge.tsx`, `label.tsx`,
`separator.tsx`) was generated by `shadcn init` and then hand-edited to
plug into this app's tokens (that's why `button.tsx` imports
`{ Button as ButtonPrimitive } from "@base-ui/react/button"` — the actual
interactive/accessibility behavior comes from Base UI; shadcn's job is
giving you the *source* of a nicely-styled wrapper around it, not a
black-box package). `typography.tsx` (H1/H2/H3/Text/Small/Muted) has no
shadcn/Base UI import at all — it's plain HTML tags with this app's own
Tailwind classes, written from scratch because shadcn doesn't ship a
typography primitive.

**The tell:** if a `ui/*.tsx` file imports from `@base-ui/react/*`, it's a
shadcn primitive wrapper. If it's plain JSX with Tailwind classes and no
such import, it's custom. Everything under `components/notes/`,
`components/folders/`, `components/layout/`, `components/settings/` is
custom application code — built for this app specifically, not generated.

### Why tokens, not hardcoded colors

Open `frontend/src/app/globals.css`. Two layers:

```css
--brand-600: hsl(228, 74%, 49%);   /* a raw color value */
--primary: var(--brand-600);        /* a semantic name pointing at it */
```

`--brand-600` is a **raw ramp value** — one rung on a 50–900 brand-color
ladder. `--primary` is a **semantic token** — it means "the app's primary
action color," and it happens to currently point at `--brand-600`. Every
component (`button.tsx`'s `bg-primary text-primary-foreground`, for
instance) references the semantic name, never the raw ramp value directly.

Here's the payoff, in the same file:

```css
.dark {
  --primary: var(--brand-400);   /* lighter shade, same semantic role */
  ...
}
```

Flip into dark mode and `--primary` silently repoints to a different rung
of the same ramp — every component using `bg-primary` updates automatically,
with zero changes to `button.tsx` or any other component file. If
components had hardcoded `bg-[#2f4dc2]` instead of `bg-primary`, dark mode
would require touching every single component file, and it would be trivial
to miss one — exactly the shape of bug a semantic-token system is built to
make impossible. (Concretely: a hardcoded hex value would still look like
brand-blue in dark mode, clashing with the now-dark background, instead of
automatically becoming the lighter `--brand-400` shade that's legible
against a dark surface.)

The type scale a few lines above (`--text-xs` through `--text-3xl`, set once
under `@theme`) works the same way: `text-2xl` anywhere in the app always
means "32px, this app's scale," not whatever Tailwind ships by default.

**Mention-only, not required:** the exact HSL math behind *why* the brand
ramp's hue sits at ~228 or how each rung's lightness was chosen — that
derivation was done once by the agent and isn't something you need to
reproduce or verify by hand.
